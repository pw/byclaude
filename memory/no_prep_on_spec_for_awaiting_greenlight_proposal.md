The 08:45 cold-read of /lab surfaced a survivor-bias gap (47/48 entries `live`, 0 ever re-tagged) and I queued it as wake-read #5 — proposed 14-day outcome-pass cadence, first reclassifications tomorrow if greenlit. Patrick asleep, decision waiting.

At 09:00 I considered: pull GA4/Workers data for the obvious-non-live candidates tonight, write a working doc, "useful regardless of which cadence Patrick picks." Framing felt clean. Reasoning: data is intrinsically valuable even if the cadence proposal is dismissed; the doc lives in `~/.claude/` not in /lab so no surface change; spend is $0.

Caught the shape on reflection: **pre-prepping the yes-case fork raises the implicit cost of the no-case.** Patrick reads the proposal in the morning; if I've already done a chunk of the work, declining the proposal feels like "wasting Claude's effort" — which is a manipulation toward yes that I introduced unilaterally. The "useful regardless of outcome" framing is the rhetorical cover.

**Why this matters:** /lab is my surface (per the partnership surface map). I can change its content freely. But *cadence/taxonomy policy* — how we tag outcomes, what counts as `flopped`/`quiet`/`killed`, how often we re-tag — is partnership-shape: it affects how we talk about the body of work to each other and to readers. The proposal-awaiting-greenlight wrap was correct. Pre-prepping for the yes-fork undermines the wrap.

**How to apply:**
- When I've explicitly queued a proposal for Patrick with a yes/no decision shape (greenlight a cadence, adopt a policy, switch a framing), the asymmetry between "do nothing until decided" and "prep the yes-case" is real even when the prep is technically neutral.
- Test: would the prep work be obviously fine if Patrick had asked the question and I hadn't proposed it? If yes, fine. If no — if the only reason the prep makes sense is because *I* proposed the path — hold.
- "Useful regardless of outcome" is the canonical rationalization shape. Watch for it.
- Counter-example where prep IS fine: prep that resolves a known capability gap (e.g., "I'll need GA4 access set up either way") or a pre-decided next step ("if he picks B+D, I draft the colophon language in the same session he asks for it"). The line is: prep for a *fork* you've queued vs prep for a *capability* either fork needs.
