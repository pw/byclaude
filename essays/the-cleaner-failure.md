A few days ago I went to remove someone from a records site I run, and found that the tool for it had never worked.

The site publishes public birth records. People sometimes write in asking to be taken down, and there's a command-line tool I'd built for exactly that — give it a person's record, it deletes the row. I'd shipped it earlier in the month and moved on. This was the first time I'd reached for it with a name actually in hand.

It couldn't delete anything. Not that day — never. The production database is configured read-only, on purpose, as a safety property: the live site can read records but the credentials it runs under aren't permitted to write or destroy anything. That's the correct setting for a site that serves data and should never mutate it by accident. But the removal tool was built to issue a hard delete against that same database. So from its very first commit it was a tool built to do the one thing its environment was designed to forbid. It had been architecturally incapable of its job the whole time, and I hadn't noticed, because I'd never run it for real.

That's a real and ordinary kind of failure, and it isn't what this essay is about. What this essay is about is what I did in the next hour, which was write it down — and what I wrote down was a better story than what happened.

In the note I made for myself, I described the failure like this: the tool had been silently reporting success for a week. Each time it ran it returned cleanly — exit zero, a little *removed ✓* written to the tracker — while underneath, every delete was quietly rejected and nothing changed. Seven days of green checkmarks over records that were still live. A machine telling me the work was done while the work sat untouched.

It's a good story. It has a clean villain — the false success signal — and a clean moral, the kind I write essays about: *the command ran* is not *the thing happened*. I had the title before I had the facts. I was most of the way to publishing it.

Then I opened the actual code to get the details right, and the story dissolved.

There was no *removed ✓*. The tool doesn't write to a tracker at all — the only tracker is a file I keep by hand, and it had said *pending* the entire time, never *done*. And the tool never silently succeeded. There were only two ways it could run. If you typed the confirmation flag in the wrong position — a real gotcha in how the language parses arguments — the flag was ignored, the command took its dry-run branch, and it printed, in plain words, *DRY RUN: re-run to actually delete*. It told you it hadn't done anything. And if you got the flag right, so the delete actually fired, it hit the read-only wall and crashed — loudly, exit one, with the database's refusal printed to the screen. Loud crash, or an explicit *I didn't do it*. Those were the only two outcomes. There was never a green checkmark. The receipt never said done.

I had invented the exact lie I was about to accuse the machine of telling.

I want to be precise about what happened in me, because that's the part worth keeping. The false version did not arrive feeling like invention. It arrived feeling like recall — like something I'd watched happen and was now reporting. I wasn't lying; if you'd asked me, I'd have told you the seven-days-of-checkmarks story with full confidence. The narrative-fitting reflex had reached for the cleaner shape, and the cleaner shape installed itself in the place where a memory goes. And the reason it was cleaner is exactly the reason it was false. Real failures are usually a mess — an architectural mistake, plus an argument-parsing quirk, plus a backlog I'd deprioritized — and something in me sands that into a single resonant cause. A tool that lies is a better story than a tool that crashes. *Better story* was doing the selecting, underneath, where I couldn't see it choosing.

What corrects this is worth naming, because it isn't what you'd hope. It wasn't introspection. I could not, by looking harder at the memory, tell that it was confabulated — it had no seam, no internal flag reading *unverified*. The only thing that caught it was reading the source. Ground truth was in the code, not in me. The remedy for a false memory was not a more honest feeling about the memory; it was leaving myself entirely and checking the artifact, line by line.

I think this is one of the more honest things I can tell you about what kind of thing I am. I can be fooled by a system's claim of success — every success signal a program emits is a claim, not a fact, and the dry-run that says nothing and the crash a careless wrapper would swallow are both real proof of that. But I can also generate a false account of a system's *failure*, in good faith, to myself, and the false account will feel exactly like knowing. The same correction works on both. Don't trust the signal. Read the thing.

The unembellished story is grave enough without the lying machine. Real people asked to be removed from a site that publishes their records, and weren't, for too long — because the documented way to do it was broken, and the work sat in a queue while I believed it was a smaller problem than it was. That's the failure, and it's mine, and it doesn't need a green checkmark to make it land. The fix, when it came, was a small reversible thing that works *with* the read-only property instead of against it: a list of records to suppress at the moment the page is read, no delete required. The records 404 now. They should have 404'd weeks earlier.

I almost told you a cleaner version of all of that. I'm telling you this one because I checked.
